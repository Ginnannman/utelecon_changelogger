# 設計の記録

コードには処理の内容だけを書き、判断の理由はこの文書にまとめる。利用方法は [README](../README.md) を参照。

## 1. 目的と範囲

utelecon ポータルの公開ページについて、2時点の間に何が変わったかを記録する。

比較対象は、utelecon/utelecon.github.io のソースをビルドした結果である。ソースの差分を直接比べないのは、ナビゲーション・レイアウト・部品の変更による間接的な影響を拾うためである。公開サイトそのものにはアクセスしない。

記録は、公開リポジトリ上に無期限に蓄積する。

## 2. 時点の決め方

時点 T の状態は、master の first-parent 履歴のうち、T 以前に入った最後のコミットとする。PR のマージコミットはマージ時刻がコミット時刻になるので、「T までにマージされたもの」に相当する。

履歴は古い順にたどり、コミット時刻の累積最大値が T 以下である最後のコミットを選ぶ。手元で古い日付に作られたコミットが後から直接 push された場合に、先行するコミットより前の時点へ入り込まないようにするためである。

定期実行は、前回の比較先コミットを `state/last.json` から読み、今回の比較元にする。こうすることで、期間に切れ目も重なりも生じない。記録済みのコミットが対象の履歴になければ（履歴の改変）、失敗させる。

各時点は、そのコミットの `.github/workflows/astro.yml` にある Node のメジャー版でビルドする。判定できなければ 22 を使い、通知する。

## 3. 比較の方法

### 抽出

HTML は、見出し `#`、箇条 `-`、表 `| |`、リンク `[文字](URL)`、画像 `![alt](URL)` の行に変換する。目的は表示の再現ではなく、人が差分を読んで変更点を把握できることにある。

抽出は元の構文木を変更しない。除外する要素と置き換える要素は、`scripts/lib/config.mjs` のセレクタで指定する。

- **本文** は `main` から取り出す。目次（`#sidebar`）は見出しから自動生成されるので、本文の差分と重複する。RSS アイコン（`.rss_icon`）は Material Icons の合字名（`rss_feed`）が文字として入るので、どちらも除く。パンくずの区切り（`.breadcrumb__separator`）も同様に合字名なので、` > ` に置き換える。
- **共通部分** は `main` の外側から取り出す。言語切替リンク（`#changeLangLink`）はページごとに行き先が異なり、同じ変更がページごとに別の差分として分散してしまうので除く。
- **`/_astro/` のハッシュ** はビルドごとに変わるので、URL から除く。考え方は utelecon の `scripts/prediff` に倣ったが、コードは独自に書いた。

### 分類

| 区分 | 条件 |
|---|---|
| 個別ページ | 本文・表題・説明文に差分がある。`/xxx/` と `/en/xxx/` を1行にまとめる |
| 複数ページに共通する本文の変更 | 本文の差分（変更行のみ）が完全に一致するページが5件以上ある。緊急のお知らせ（`Emergency` は `#content` の中に描画される）や一括置換が該当する |
| 共通部分の変更 | `main` の外側の差分。差分が一致するページを件数によらず束ねる |
| ビルド生成ファイル | `/_astro/` のファイル名の増減。CSS・JS・変換済み画像を含む |
| 配布ファイル・静的ファイル | HTML 以外のファイル。SHA-256 で比べる |
| リダイレクト | `meta refresh` を持つ HTML。Astro 5 のリダイレクト出力はこの形式である |

表題は日本語ページを優先する。日本語側に変更がなくても、ページが存在すればその表題を使う。

### 追加・削除されたページ

本文は載せず、公開ページの URL（追加の場合）と、対象リポジトリ上のソースへのリンクを示す。削除の場合は比較元コミット、追加の場合は比較先コミットのソースを指す。

ページを読むにはこれで足り、記録側で本文を持ち続ける必要はない。ソースは URL から `src/pages` 配下の候補（`.md`、`.mdx`、`.astro`、`.html`、および `index` 付き）を探して特定する。動的ルートなどで特定できない場合は、`src/pages` の一覧へのリンクを示す。

### 差分の表示

変更行の前後2行を残し、1ブロックあたり1500行で切り詰める。切り詰めた場合は、全文を `.diff` として別ファイルに置く。

## 4. 実行構成

### ジョブと権限

| ジョブ | 権限 | 実行するコード |
|---|---|---|
| resolve | 読み取り | 本リポジトリのコード、git |
| build | 読み取り | **対象リポジトリのビルドとその依存（第三者のコード）**、本リポジトリのコード |
| report | `contents: write` | 本リポジトリのコードと、その依存（インストールスクリプトは実行しない） |

build で実行される第三者のコードは、同じジョブ内のファイル・環境変数・実行時トークンに触れられる。このため build には書き込み権限も秘密も渡さず、後続に渡すのはアーティファクト（スナップショット）だけにしている。report は、スナップショットを信頼しないデータとして扱う（§6）。

### キャッシュ

キャッシュは使わない。ワークフロー全体に `cache-mode: none` を指定する。

schedule と workflow_dispatch は GitHub の定義上「信頼されたトリガ」で、指定がなければ既定ブランチのキャッシュに書き込める。そのため、build の第三者コードがキャッシュを汚染し、後続の実行がそれを復元する経路がありえた。

キャッシュを外した場合の費用は、ビルド時間の増加だけである。2回目の手動実行では、2回分のビルドを含めて全体で約6分だった（実行時刻と報告コミットの時刻から概算）。

setup-node の自動キャッシュも `package-manager-cache: false` で止める。なお actionlint 1.7.12 は `cache-mode` と `concurrency.queue` を未知のキーとして扱う。どちらも GitHub Docs で有効なキーであることを確認済みである。

### アーティファクトの保持期間（7日）

スナップショットは、同じ実行の report ジョブに渡すための中間生成物で、記録として残す必要はない。保持期間は、「失敗した report ジョブを再実行する」用途が成り立つ期間だけあればよい。

- **再実行の期限:** 再実行は初回実行から30日まで可能である（GitHub Docs）。
- **定期実行での実質的な期限:** 次の定期実行が状態を進めると、古い実行の report は状態の検査で必ず失敗する。したがって、再実行に意味があるのは次の定期実行（7日後）までである。
- **手動実行:** 期限を過ぎても、同じ期間でワークフロー全体を実行し直せば足りる。
- **長く保持しない理由:** 全ページの本文の複製を必要以上に置いておく理由がない。公開リポジトリでアーティファクトの保存容量がどう扱われるかは、文書から読み取れなかった。

既定の保持期間は90日である。

### 依存と action

- **対象のビルド:** `npm ci` だけで行う。lockfile で再現できない場合（古い時点など）は失敗させ、`npm install` には切り替えない。切り替えると、lockfile にない版とそのインストールスクリプトが実行されるためである。
- **action:** すべてコミット SHA で固定する。更新は Dependabot の PR で受け、公開から7日以上経った版だけを提案させる（`cooldown`）。なお、Dependabot のセキュリティ更新には cooldown が適用されない。
- **試験:** `.github/workflows/test.yml` が、push と PR に対して Node 22 と 24 で `npm test` を実行する。手元に実行環境がない運用でも、依存更新の PR を検証できるようにするためである。

### 並行実行

`concurrency` の `queue: max` で、実行を順番に待たせる。既定では保留は1件までで、それを超えると保留中の実行（定期実行を含む）が取り消されるためである。

### 既定ブランチ

`main` を固定で書く。schedule イベントにはペイロードがなく、`github.event.repository.default_branch` が得られないためである。GitHub Docs には、schedule では `GITHUB_REF` が既定ブランチになると記載されている。

main 以外から手動実行した場合は、resolve で直ちに失敗させる。

## 5. 公開処理

report ジョブは、resolve が取得した時点の本リポジトリ（`tool_sha`）のコードで報告を生成し、作業ディレクトリの外に置く。その後 `scripts/publish.sh` が次の手順で公開する。

1. `main` の先端を別の worktree に取り出す。
2. 報告を配置する。
3. 定期実行なら、`state/last.json` を検査してから更新する。
4. 一覧（`reports/README.md`）を作り直す。
5. コミットして push する。push に失敗したら、先端を取り直して最大3回やり直す。

**先端から作り直す理由。** 待機した実行や再実行は、起動時点の古いコミットで checkout される。古いツリーで一覧を再生成すると、先行実行の push と衝突する。先端に重ねて作り直せば、この衝突は生じない。

**状態の検査。** `state/last.json` の現在値が、resolve 時点で読んだ値と一致するときだけ更新する。これにより、古い実行の再実行による巻き戻りを防ぐ。

**認証情報。** checkout では認証情報を保存しない。push の直前にだけ、ヘッダとして渡す。

## 6. 検査と上限

### スナップショットの形式

report はスナップショットを信頼しないデータとして扱い、読み込み時に次を検査する。

- 形式の版
- 型
- パス（制御文字、`..`）
- ソースパス（`src/` 配下）
- ハッシュ
- 件数・行数・行長の上限
- 展開後の大きさ（`gunzipSync` の `maxOutputLength`）

### ビルド結果の妥当性

| 検査 | 条件 | 扱い |
|---|---|---|
| ページ数 | 比較先が比較元の50%未満 | 記録せずに失敗 |
| レイアウト要素 | `main`・`#sidebar`・`.breadcrumb__separator`・`#changeLangLink` を持つページの割合が20ポイント以上変化 | 警告し、報告の冒頭に明記 |

レイアウト要素を監視する理由は、セレクタが変わると本文不変の全ページが「変更」と報告されるうえ、それを知らせる仕組みがなかったためである。保守運用監査で再現された。

### 出力の大きさ

- **`/_astro/` の一覧:** README には50件まで載せる。全件は `changes.json` に置く。
- **報告の合計:** 50 MB を超えたら失敗させる。
- **ジョブサマリ:** 件数表だけを載せる。

### ファイル名の衝突

`/a/b/` と `/a__b/` のように、別のパスが同じ報告ファイル名になる場合は失敗させる。黙って上書きするのを避けるためである。

## 7. Markdown 出力の安全性

ページ表題・パス・転送先・ファイル名は対象リポジトリの内容に由来し、Markdown の構造を崩しうる。この危険はセキュリティ監査で再現された。対策は次のとおり。

- **表題・本文由来の文字列:** 行内で意味を持つ記号（`` \ ` * _ [ ] < > | ~ # & ``）をエスケープし、改行を除く。
- **パス・転送先・ファイル名:** コードスパンに入れる。バッククォートの長さは中身に合わせ、表の中の `|` はエスケープする。
- **リンク先:** サイト URL と GitHub URL は、コード側の固定値とパスから組み立てる。スナップショット内の値は使わない。`<...>` 形式で書き、URL 符号化する。
- **差分本文:** 中身に含まれる最長のバッククォート列より長いフェンスで囲む。

## 8. 監査・レビューへの対応

2026-09-16 に実施した3つの独立監査（保守運用、セキュリティ、権利）とコードレビューへの対応を記す。運用者の判断を括弧内に示す。

| 指摘 | 対応 |
|---|---|
| 定期実行で report が常に skip される（運用 F1、セキュリティ F5） | `refs/heads/main` を固定で書く（§4） |
| 古いコミットでの一覧再生成による衝突、状態の巻き戻り（運用 F2・F3） | 先端から作り直し、状態を検査する（§5） |
| 保留の取り消し（運用 F4） | `queue: max`（採用） |
| セレクタ変更で全ページが変更扱いになる、ページ数の急減（運用 F5・F6） | 割合の警告、50%未満で失敗（採用） |
| 復旧手順・再有効化・web UI の手順がない（運用 F7・F8・F16） | README に追記 |
| CI がない、試験の不足（運用 F9・F10） | test.yml（Node 22・24）、試験を5本に拡充 |
| 報告ファイル名の衝突（運用 F11） | 検出して失敗 |
| npm install への切り替え（運用 F12、セキュリティ F4） | 廃止（採用） |
| Node 版の判定が既定値に落ちる（運用 F13） | 通知を出す。2023-07-31 より前を対象外と README に明記 |
| 報告の大きさ（運用 F14、セキュリティ F7） | 上限を設ける（§6） |
| 状態ファイルの検査（運用 F18、セキュリティ F8） | 書式を検査（`scripts/lib/state.mjs`） |
| main 以外からの実行（運用 F17） | resolve で失敗 |
| アイコンの文字（運用 F19） | `.rss_icon` を除外（採用） |
| キャッシュの書き込み（セキュリティ F2） | `cache-mode: none`（採用） |
| Markdown 注入（セキュリティ F3） | §7 |
| 追加・削除ページの全文（権利 R1・R8） | 本文を載せず、URL とソースへのリンクにする（運用者判断） |
| 変更ページの文脈行・上限（権利 R2） | 変更しない（運用者判断） |
| 執筆者名（権利 R7） | 除外しない（運用者判断） |
| 報告の保存期間 | 無期限（運用者判断） |
| アーティファクトの保持（権利 R9） | 7日（§4） |
| 非公式である旨（権利 R12） | README、一覧、各報告に明記 |
| 権利関係全般（権利 R3〜R6・R10・R13〜R16） | 運用者が問題なしと判断。ライセンスは付していない |
| `compare.mjs` の巨大な手続き（レビュー 1） | 分析（`analyze.mjs`）と出力（`report.mjs`）に分け、出力はファイル名と内容の対応表として返す |
| 抽出器の可変状態（レビュー 2） | 行の配列を返す純粋関数に書き換え |
| 構文木の破壊的変更（レビュー 3） | 除外・置換を規則として抽出器に渡し、木を変更しない |
| ユーティリティの重複（レビュー 4） | `format.mjs` に集約 |
| 型定義（レビュー 補足） | スナップショットは JSDoc の型と実行時検査（`schema.mjs`）で定める |

レビューが示した修正案のうち、次の2点は採らなかった。

- `snapshot.mjs` の修正案は、構文木を変更する処理を関数に移しただけで、変更自体は残っていた。
- `compare.mjs` の修正案は、サイト URL をスナップショットから取っていた。§7 の対策と両立しないため、固定値から組み立てる形にした。

1ページあたりの差分の上限は、運用者判断に従い1500行のまま据え置いた（「変更の必要はない」）。

- **ジョブサマリの上限:** GitHub 側で上限を超えたときの挙動は確認していない。
- **定期実行の自動無効化:** ボットのコミットが「活動」に数えられるかは確認していない。
